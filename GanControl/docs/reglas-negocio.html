0. Levantar el entorno de desarrollo

Para ejecutar todo el sistema de GanControl en un ambiente local es necesario iniciar los tres proyectos principales:

1
Aplicación móvil (Expo)
Abrir una ventana de CMD en la carpeta GanControl.App y ejecutar: 
npx expo start
Este comando inicia el servidor de desarrollo de Expo para la aplicación móvil.
2
Aplicación Web (React/Vite)
Abrir una ventana de CMD en la carpeta GanControl.Web y ejecutar: 
npm run dev
Este comando inicia el servidor de desarrollo de la aplicación web.
3
API Backend (.NET)
Abrir una ventana de CMD en la carpeta GanControl.API y ejecutar: 
dotnet run
También puede abrirse la solución en Visual Studio y ejecutarse directamente desde el IDE.
Orden recomendado: iniciar primero la API, después la aplicación Web y finalmente la aplicación móvil.

1. Visión general

GanControl es un sistema de administración de ranchos ganaderos pensado para productores en México (usuarios poco técnicos: el app debe ser muy intuitiva, con textos grandes y pasos simples). El backend es un API REST en ASP.NET Core (.NET 9) con acceso a SQL Server mediante repositorios con SQL directo (sin EF).

El modelo central es: una cuenta (con un plan) tiene ranchos; cada rancho tiene corrales/potreros, animales y usuarios con un rol por rancho. Todo lo que le pasa a un animal se registra como un evento (vacuna, parto, venta, muerte…). Cada tipo de evento tiene un handler en el backend que:

  • Valida antes de guardar (¿el animal está activo? ¿es hembra? ¿está gestante?…)
  • Ejecuta efectos secundarios después de guardar (cambia el estado del animal, crea recordatorios en la agenda, da de baja, etc.)
Idea clave del diseño: el frontend solo manda el evento con sus datos; el backend se encarga de mover los estados del animal y de crear los recordatorios. Así el usuario del rancho no tiene que acordarse de nada: registra "inseminación" y el sistema le agenda solo el "revisar celo" y el "diagnóstico de gestación".

5. Crear y administrar animales

Pasos para registrar un animal nuevo (POST /api/Animales)

1
Acceso: el usuario debe tener rol en el rancho y no ser visor.
2
Campos obligatorios: ranchoId, especieId, codigoArete (no vacío) y sexo = M o H.
3
Arete único: no puede existir otro animal con el mismo arete en ese rancho.
4
Límite del plan: se valida contra los animales activos del rancho (sección 4).
5
Evento inicial automático: según origen se crea, en la misma transacción que el animal (todo o nada):
  • origen = "nacido" (default) → evento Nacimiento con fecha = fecha de nacimiento (o ingreso, u hoy), peso = peso al nacer, y datos_json = {"madreId":…, "padreId":…} si vienen.
  • origen = "comprado" → evento Compra con fecha = fecha de ingreso (u hoy), monto = precio de compra, peso, y datos_json = {"vendedorId":…} si viene.

Editar, dar de baja y eliminar

  • Editar (PUT): mismo permiso que crear; si se cambia el arete, se re-valida la unicidad excluyendo al propio animal.
  • Dar de baja (POST /baja): motivos válidos: muerte, venta, robo, otro. Pone activo=0, fecha_baja, motivo_baja. Bloqueado para visor y capturista.
  • Eliminar (DELETE): soft delete (deleted_at), solo owner/admin. Nota: normalmente la baja correcta es por evento de muerte o venta, que además limpian lotes y agendas.

7. Reglas generales para TODOS los eventos

Antes de aplicar las reglas específicas de cada tipo, EventoService.CrearAsync valida siempre:

  • El usuario tiene rol en el rancho y no es visor.
  • El animal existe y pertenece al rancho indicado en el request.
  • El título es obligatorio.
  • El tipoEventoId debe existir en cat.tipos_evento; con su clave se busca el handler correspondiente.
  • Si el tipo tiene handler, se ejecutan sus validaciones; si no tiene handler (pesaje, observación, nacimiento, compra…), se guarda sin validación extra.
  • Validación estricta de datos_json (DatosJsonValidator): el JSON debe cumplir el esquema del tipo de evento. Si está mal formado, trae un campo desconocido (ej. typo "produto") o un tipo incorrecto (ej. dosis: "cinco"), el evento NO se guarda y el API responde con el error. El JSON válido se re-serializa en camelCase y sin nulls, para que todos los eventos queden con formato uniforme.

Después de guardar, se ejecutan los efectos secundarios del handler (cambios de estado, agendas, bajas, movimientos…).

Eliminación de eventos

  • Soft delete, solo owner/admin.
  • NO se pueden eliminar (HTTP 409) los eventos con efectos permanentes: muerteventaparto trasladomarcajecompra — habría que hacer la "reversión" correspondiente (aún no implementada).

Convención de datos_json

// El frontend serializa en camelCase SOLO los campos específicos del tipo.
// Ejemplo para una vacuna:
{
  "producto": "Bacterina triple",
  "dosis": 5, "unidadDosis": "ml",
  "via": "intramuscular",
  "lote": "L-2241", "laboratorio": "Zoetis",
  "fechaCaducidad": "2026-12-01",
  "notas": "Sin reacción"
}
// peso, monto, numeroCrias, veterinarioId, compradorId, proximaFecha,
// fecha, hora, titulo, descripcion ya tienen columna propia: NO van aquí.

💰 Venta comercial id 14 · clave: venta 🔒 no eliminable

Validaciones

  • Animal activo (no se puede vender dos veces).

Efectos

🚚 Traslado general id 17 · clave: traslado 🔒 no eliminable

Validaciones

  • Animal activo.
  • datos_json.destinoCorralId es obligatorio.
  • Si es entre ranchos (destinoRanchoId distinto al actual): el usuario debe tener rol en el rancho destino y el corral destino debe pertenecer a ese rancho.

Efectos

  • Actualiza animales.corral_id (y rancho_id si es inter-rancho).
  • Crea un registro en animal.movimientos_animal (origen = origenCorralId del JSON o el corral actual antes del cambio).
  • Inter-rancho: el historial de eventos, agendas y lotes NO se migran automáticamente (operación de backoffice pendiente).

datos_json (DatosTraslado)

  • destinoCorralId ⭐ obligatorio · origenCorralId, origenRanchoId, destinoRanchoId
  • motivo: engorda | pastoreo | venta | cuarentena
  • distanciaKm · transporte: camion | pie | remolque · responsable · notas
🏷️ Marcaje / Areteo general id 18 · clave: marcaje 🔒 no eliminable

Validaciones

  • Animal activo.
  • datos_json.tipoMarca es obligatorio: arete | chip | tatuaje | fierro.
  • codigoNuevo es obligatorio si tipoMarca es arete o chip.
  • Si es arete: el código nuevo debe ser único en el rancho (se permite re-aretar con el mismo código del propio animal).

Efectos

  • arete → actualiza animales.codigo_arete.
  • chip → actualiza animales.chip_electronico.
  • tatuaje / fierro → solo queda en el JSON (no hay columna).

datos_json (DatosMarcaje)

  • tipoMarca ⭐ · codigoNuevo (⭐ para arete/chip) · codigoAnterior
  • ubicacion: oreja_der | oreja_izq | anca | lomo · motivo: ingreso | reemplazo | duplicado · notas

Validaciones

  • Animal activo (si ya está inactivo, error: posiblemente ya dado de baja).

Efectos

  • Baja del animal: activo=0, fecha_baja, motivo_baja="muerte" (con causaDetalle como nota).
  • Estado de salud → muerto.
  • Lo saca de todos los lotes y cancela sus agendas futuras.
  • Alerta de brote: si la causa es enfermedad y en el mismo corral hay ≥ 2 animales más con enfermedad en los últimos 14 días → se escribe una alerta en el log (pendiente: notificación push/email a veterinarios y admin).

descripcion, veterinario_id.
